# Web Attack Detection Engine（Web 攻击检测引擎与绕过对抗测试）

[中文](#中文说明) | **A lightweight Web attack detection engine in pure Python, plus a framework that automatically attacks its own rules.**

一个用纯 Python 实现的轻量级 Web 攻击日志检测引擎，以及一套**自动攻击它自己的绕过测试框架**。

设计目标不是"做一个能上生产的 WAF"，而是回答两个问题：

1. 一套正则规则在真实日志上到底能检出多少、误报多少——**用带真值标签的数据算出来**，而不是凭感觉。
2. 这套规则的抗绕过能力有多强——**写一个脚本自动攻击它**，把盲区一条条逼出来。

最终数字（本机实测，可一键复现）：

| 指标 | 数值 |
|---|---|
| 日志样本 | **452 条**（自建靶场真实访问日志，每条带真值标签） |
| 检出率 Recall | **100.0%**（命中 72 / 漏报 0） |
| 误报率 FPR | **0.0%**（正确排除 380） |
| 对抗测试 | **30 种绕过手法 × 346 个用例** |
| 绕过率 | **0.0%**（12.3% → 0%） |
| 协议层专项 | **8/8 检出** |
| 采集层专项 | **0/5**（已知边界，单列不计入绕过率） |

> 所有数字的前提都是「在我自建的样本上」。这不是谦虚，是事实——见 [已知局限](#已知的局限诚实清单)。

## 为什么写这个

大多数"我搭了一个 WAF / IDS"类项目停在"规则写完了，跑通了"。但有两个问题几乎没人回答：

- **指标是真是假？** 攻击流量如果是自己按课本写法造的，规则当然全中。
- **规则被变形后还灵不灵？** 真实攻击者的载荷一定会变形。

本项目把这两点做成了可复现的流程：

- `traffic_gen.py` 产生的每条流量都写一条真值（`ground_truth.jsonl`），所以能算 TP / FP / FN / TN，能定位每一条漏报。
- `mutate.py` 用 30 种真实绕过手法对 16 个基础载荷做变形，生成 346 个用例，自动统计"哪些手法能打穿规则"；并对每个变形做**有效性校验**，确保"变形后仍是同一个攻击"。

## 快速开始

```bash
# 1) 依赖：评估与对抗测试只需标准库；靶场需要 flask、requests
pip install flask requests

# 2a) 不启靶场，直接用内置样本评估（最快）
python detect.py --evaluate        # 检出率 100.0% / 误报率 0.0%

# 2b) 或跑完整实验：靶场 + 真实流量 + 检测 + 报告
python vuln_app.py                                     # 终端 1
python traffic_gen.py --normal 300 --attack 90 --burst --brute
python run_pipeline.py                                 # 输出 检测报告.md 与 dashboard.html

# 3) 对抗测试：让脚本攻击自己的规则
python mutate.py                                       # 输出 对抗测试结果.json
```

Windows 用户可直接运行 `scripts/一键运行.bat`。

## 检测引擎设计

### 规则

| 类型 | 规则 | 说明 |
|---|---|---|
| 特征 | R1 SQL 注入 | 联合查询、布尔/时间盲注、堆叠查询 |
| 特征 | R2 扫描器指纹 | sqlmap / nmap / nikto 等 UA |
| 特征 | R3 命令注入 | 分号/管道后接系统命令、反引号、`$()` |
| 特征 | R4 路径遍历 | `../`、`..%2f`、绝对路径敏感文件 |
| 特征 | R5 XSS | `<script`、`onerror=` 等 |
| 特征 | R6 敏感路径 | `.git`、`/.env`、`/admin`、备份文件 |
| 行为 | R7 请求频率突增 | 滑动窗口内同一 IP 请求数超阈值 |
| 行为 | R8 认证爆破 | 登录端点连续失败次数超阈值 |

### 归一化层（核心）

规则数量从头到尾**一条没加**，抗绕过覆盖率却从 87.7% 提到 100%——提升全部来自把"语义等价但字面不同"的写法折叠成同一种形态：

1. JSON/JS `\uXXXX` 转义还原、UTF-7 还原
2. UTF-8 超长编码还原（`%c0%af` → `/`）与 URL 多次解码，**循环到稳定**
3. 剥离 SQL / HTML 注释（`/**/`、`/*!50000*/`）→ **生成"当断词"与"当空格"两个候选**
4. Shell 空白变量还原（`${IFS}`、`$IFS` → 空格）
5. 空白符统一（`%09 %0a %0b %0c %a0`、全角空格 → 普通空格）
6. Unicode 同形字映射、NFKC 全角归一、`CHAR(117,110,...)` 折叠、双写关键词折叠
7. 路径分隔符统一、路径段分号剔除（`..;/`）、多重空白压缩

**顺序是归一化的第一性问题**：先 URL 解码会把 `%c0%af` 解成两个 `U+FFFD`，载荷被自己改坏，后面的规则再也匹配不到。必须先还原超长编码再解码，且要循环。

### 语义层

归一化解决的是"字面不同"，语义层解决"字面毫无共同点"：

- 词法化 → 操作符等价归一（`||` → `or`）→ **常量折叠**（`2>1` 与 `1=1` 折叠为同一标记）→ 序列匹配

这几十行换来的是语义层的一部分覆盖，代价远小于引入完整语法树。

## 对抗测试：数字是怎么变化的

| 轮次 | 绕过数 | 绕过率 | 本轮改动 |
|---|---|---|---|
| 初始（19 手法 / 186 用例） | 23/186 | **12.3%** | — |
| 第一轮 | 8/186 | 4.3% | 修 R3 正则缺陷 + 建立七步归一化 |
| 第二轮 | 4/186 | 2.2% | 修超长编码与 URL 解码的顺序 + 注释双候选 |
| 第三轮 | 1/186 | 0.5% | 修贪婪匹配 `{2,3}` → `{2}` + 解码轮数 3→5 |
| **补测协议层（346 用例）** | **反弹** | **7.8%** | 新增 11 种手法与"换字段"用例 |
| 第四轮 | 10/346 | 2.9% | 全字段扫描 + `\uXXXX`/UTF-7/CHAR()/NFKC/同形字归一化 |
| **第五轮** | 0/346 | **0.0%** | 修测试脚本截断 bug + 双写折叠 + 语义层 S1–S5 |

### 最有价值的三件事

**1. 7.8% 那次反弹**

新增的协议层用例里，4 个完全隐身：

```
载荷放进 Cookie            ❌隐身
载荷放进 X-Forwarded-For   ❌隐身
载荷放进 Accept-Language   ❌隐身
载荷放进自定义 Header       ❌隐身
```

这 4 个用例的载荷**一个字符都没变形**，照样看不见——因为第一版检测函数硬编码只读 `url / ua / body / referer` 四个字段。

**不要用白名单定义"攻击会出现在哪"**：载荷位置由攻击者决定。修复方式是遍历所有字段（含嵌套 headers），协议层 8/8 恢复检出。这也说明——**只在自己想到的维度里测，测的是我的想象力上限，不是系统的强度。**

**2. 8/10 的"盲区"是测试脚本自己的 bug**

第五轮发现，变异函数里有这么一行：

```python
head = s[:12]                 # 只取前 12 个字符
return "char(%s)" % codes     # 后面的载荷，直接丢了
```

它把载荷截断了。还原出来的不是完整攻击——规则不认它是对的，MySQL 也不会执行它。我拿自己脚本造出来的残片当成了系统的能力边界。**测试工具本身也必须被测**，所以 `mutate.py` 加了 `variant_effectiveness` 有效性校验。

**3. 上一版那个 100% 有一部分是碰巧的**

行为事件的时间戳用的是运行时刻（`now_str()`），而请求时间来自日志。下游按窗口做关联——第一次跑恰好几分钟内就检测，对上了；隔几小时再跑差 27112 秒，永远对不上，数字掉到 88.9%。修法是让事件携带触发它的请求时间。

### 两类根因要分开

判断标准是"原始写法能不能被检出"：

- **不能** → 规则设计缺陷（如 R3 要求 `;` 后必须有空白，`;cat${IFS}...` 整类 11/11 全绕过）
- **能，变形后不能** → 真正的绕过手法，靠归一化解决

## 已知的局限（诚实清单）

- **数据是自建的。** 452 条流量来自 `traffic_gen.py`，不是真实生产流量。100% 只在自己的数据集上成立，真实值一定更低。
- **只有规则 + 归一化，没有语法树。** 分块传输编码、HTTP 请求走私、慢速攻击、多参数拼接、HTTP/2 头部压缩差异——一个都没测。
- **采集层 5 类盲区修不了**：URL 截断、body 未采集、分块传输、请求走私、HTTPS 只看 SNI。这些是**输入里根本没有载荷**，改检测逻辑无用，只能改采集层。它们在测试中单列、不计入绕过率，避免把数据问题当规则问题去修。
- **行为规则依赖窗口**：爆破需要累计到阈值才触发，用请求级口径衡量它会得出错误的漏报结论。
- **没有响应动作。** 项目只做检测与告警，不做阻断。
- **ELK 部分未在真实集群验证**：`docker-compose.yml` 与 ES 索引/ILM 配置已备好，但检测逻辑的验证是在本地文件上完成的。

## 可选：接入真 ELK

检测逻辑与存储层解耦，接 Elasticsearch / Kibana 只需替换日志来源：

```bash
docker compose up -d      # Elasticsearch + Kibana + Filebeat
# Kibana: http://localhost:5601
```

`filebeat.yml` 负责把 `access.log` 送进 ES，`detect.py` 的规则可平移为 ES 查询或 Ingest Pipeline 脚本。
启动脚本会自动导入 `es-index-template.json`（1 主分片 / 0 副本，单节点设副本会一直 yellow）与 `es-ilm-policy.json`（30 天删除）。
