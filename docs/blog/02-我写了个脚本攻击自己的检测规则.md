# 我写了个脚本攻击自己的检测规则：绕过率 12.3% → 0.5% → 7.8% → 2.9%

> 上一篇《我是怎么把检出率从 88.9% 做到 100% 的》发出来后，有个问题我一直没敢细想：
> **那个 100%，是不是因为攻击流量是我自己按课本写法造的？**
>
> 这个数字曲线就是答案。0.5% 那一段我以为是终点，
> 结果我补测了第一轮没测的协议层，它一夜回到 7.8%。

---

## 一、先承认一件事：那个 100% 含金量有限

上一篇我拿到了"检出率 100%、误报率 0%"，复盘过程也写得很诚实。但有个前提我一直没挑明：

那 452 条流量里，攻击流量是**我用最标准的写法生成的**——`union select`、`../`、`; cat /etc/passwd`，规规矩矩，像教科书插图。

真实攻击者不会这么乖。他们会做一件事：**变形**。

所以我写了第二个脚本 `mutate.py`，干的事很简单——拿我自己造的攻击载荷，施加 19 种真实绕过手法，看哪些变形能让我的规则瞎掉。

- 16 个基础载荷（SQL 注入 5 类、命令注入 3 类、路径遍历 2 类、XSS 3 类、敏感路径 3 类）
- 19 种变形手法（大小写、注释断词、URL 编码、双重编码、超长编码、空字节、`${IFS}`、反斜杠、参数污染……）
- 交叉组合，去重后 **186 个测试用例**

这个方法的正式名字叫 **bypass testing**，商业 WAF 团队每天都在做。我只是把它缩小到一个人能跑的规模。

---

## 二、第一轮结果：12.3% 绕过率，其中一条特别刺眼

```
总用例 186 条，绕过成功 23 条 —— 绕过率 12.3%
```

按大类看：

| 大类 | 用例 | 绕过 | 绕过率 |
|---|---|---|---|
| 编码/大小写 | 82 | 11 | 13.4% |
| 注释混淆 | 9 | 4 | **44.4%** |
| 路径变形 | 10 | 3 | 30.0% |
| 语义等价 | 2 | 1 | 50.0% |
| 空白符替换 | 35 | 0 | 0.0% |

但真正让我坐直的是这一行：

```
命令注入-空格绕过    绕过 11/11  (100.0%)
```

**11 个用例，全绕过——包括"原始写法"那一条。**

也就是说，这条载荷我连不变形都检不出。这不是"被绕过了"，这是**我的规则本身写错了**。

当时的命令注入正则是这样的：

```python
CMD_INJECT_PAT = re.compile(r"(?i)(;\s*(cat|ls|whoami|id|wget|curl|nc|bash|sh)\s|...)")
```

注意 `;\s*` 后面的 `\s`——我要求分号后面**必须有一个空白字符**。

而真实写法 `;cat${IFS}/etc/passwd` 里，分号后面直接跟命令，没有空格。规则不匹配，检测形同虚设。

更糟的是：这一类 11 个用例里，所有变形手法全部成功绕过。**一个规则设计缺陷，等于整类攻击对你隐身。**

这一条的价值远超那 12.3%——它说明：**我上一轮的 100% 之所以成立，只是因为我恰好没造出这种载荷。**

---

## 三、修法：不要加更多正则

面对 12.3% 的绕过，最直觉的反应是：**哪种手法绕过了，就加一条正则**。

大小写绕过了？加个大写变体。反斜杠绕过了？加个反斜杠分支。双重编码？再来一条。

这条路的终点是规则库爆炸，而且永远补不完——变形手法是无穷的，你的正则是有穷的。

我当时做的是另一件事：**把规范化层做厚**。

思路是：不同写法之所以都能成功，是因为它们在**服务端语义上等价**。既然如此，我应该在检测前把它们折叠成同一个形态，再交给正则。

规则数量不变，覆盖面指数上升。**归一化层比规则库更值得投入。**

于是有了 `deep_normalize()`，七步：

```
1-2. 超长编码还原 → URL 解码（循环）
3.   剥离 SQL/HTML 注释
4.   Shell 空白变量还原（${IFS} → 空格）
5.   各类空白符统一（%09 %0a %0b %0c %a0 → 空格）
6.   路径分隔符统一（反斜杠 → 正斜杠）
7.   多重空白压缩
```

看起来很直白。但我在这里面**踩了三个坑，每一个都是顺序或假设错了**。

---

## 四、三个坑（这部分比结果值钱）

### 坑 1：归一化步骤的顺序错了

我最初把 URL 解码放在超长编码还原前面：

```python
# 错误版本
s = urllib.parse.unquote_plus(s)      # 先解码
s = _OVERLONG_RE.sub(_decode_overlong, s)   # 再还原超长编码
```

结果 `%c0%af` 被 `unquote` 当成普通百分号编码去解，字节 `0xc0 0xaf` 不是合法 UTF-8，Python 直接把它们替换成两个 `U+FFFD`（那个经典的乱码菱形）。

**载荷被我自己改坏了**，后面的超长还原规则再也匹配不到任何东西。

调试时我打印码点才看清：

```
输入 a%c0%af%c0%afb
输出 ['0x61', '0xfffd', '0xfffd', '0xfffd', '0xfffd', '0x62']
```

正确顺序反过来：**超长编码此时还是字面上的 `%c0%af`，先还原它，再 URL 解码**。而且两者要循环，因为双重编码下第一轮解码才会露出第二轮的超长编码。

```python
# 正确版本
for _ in range(5):
    before = s
    s = _OVERLONG_RE.sub(_decode_overlong, s)   # 先还原超长
    s = urllib.parse.unquote_plus(s)            # 再解码
    if s == before:
        break
```

顺带还有个贪婪匹配的坑：正则最初写成 `{2,3}`，遇到 `%c0%af%c0%af` 会被贪婪切成 3 字节去解，得到乱码而不是两个斜杠。改成严格 `{2}` 从左往右扫才对。

### 坑 2：注释在不同位置扮演不同角色

我第一版把所有 `/**/` 一律删成空串。然后发现 SQL 注入还在漏。

原因是注释有两种身份：

```
un/**/ion        ← 注释在关键字中间，是"断词"，应该删掉 → union
1/**/union       ← 注释在词之间，是"代替空格"，应该换成空格 → 1 union
```

我一律删成空串，第二种就变成了 `1union`，正则里的 `\s+` 匹配不到。

这里我纠结了一下：要不要写个判断逻辑去猜"这个注释是断词还是空格"？

最后我没有猜，而是**两个候选都生成，都拿去匹配**：

```python
blob = (raw + " " + deep_normalize(raw)
             + " " + deep_normalize(raw, comment_to_space=True))
```

这个取舍我想清楚了：**与其猜哪一种对，不如承认两者都可能对**。正常流量里没有 `/**/`，两个候选完全相同，所以零额外误报风险。

### 坑 3：把"规则缺陷"当成"绕过手法"来修

回到 `;cat` 那条。如果我只盯着"11 个变形全绕过"，会去研究怎么抗变形——但真正的问题是正则要求分号后有空白。

改成这样就好了：

```python
CMD_INJECT_PAT = re.compile(
    r"(?i)([;&|`]\s*(cat|ls|whoami|id|wget|curl|nc|bash|sh|chmod|python|perl)\b|...)"
)
```

空白变成可选，分隔符从只有 `;` 扩展到 `;&|\`` 和反引号。

**教训**：看到一串绕过案例时，先问"这条的原始写法能不能检出"。如果原始写法就检不出，那是规则缺陷，不是绕过问题——两种问题的修法完全不同。

## 五、结果

| 轮次 | 绕过率 | 做了什么 |
|---|---|---|
| 初始（19 手法 / 186 用例） | **12.3%** | — |
| 第一轮修复 | 4.3% | 修 R3 正则 + 建归一化层 |
| 第二轮修复 | 2.2% | 修超长编码顺序 + 注释双候选 |
| 第三轮修复 | **0.5%** | 修贪婪匹配 + 增加解码轮数 |
| **补测 11 种新手法 + 协议层（346 用例）** | **7.8%** | 协议层 4/8 隐身，绕过率反弹 |
| 第四轮修复 | **2.9%** | 全字段扫描 + 转义/UTF-7/CHAR()/NFKC 归一化 |

回归测试始终保持在**检出率 100% / 误报率 0%**——每改一次都重跑原样本，确保没有为了抗变形而引入误报。

这个很重要：**只提升抗绕过能力、却把误报搞上去了，等于没改。**

而 0.5% → 7.8% 这一段是我这轮学到的最贵的一课：**你没测过的方向，就是你最脆弱的方向。**

## 六、然后我测了第一轮故意没测的：协议层

0.5% 这个数字我没敢高兴太久。因为我在写"局限性"时列的那几个未测试手法，一直扎着我：

> 分块传输编码、HTTP 请求走私、字符集编码……我一个都没测。

于是我又加了 11 种手法（宽字节、UTF-7、全角字符、MySQL 版本注释、CHAR() 编码、`..;/`、双写关键词、Unicode 同形字……），外加一类**我第一轮压根没想到要测的：协议层**。

协议层不考变形，它问的是另一个问题：

> **同样的载荷，放在请求的其他位置，你的检测引擎还看得见吗？**

结果：

```
【协议层专项：换个字段还看得见吗】
  载荷放进 Cookie                  ❌隐身
  载荷放进 X-Forwarded-For         ❌隐身
  载荷放进 Accept-Language         ❌隐身
  载荷放进自定义 Header             ❌隐身
  JSON body 内 Unicode 转义        ❌隐身
  载荷放进 Referer                 ✅检出
  载荷放进 User-Agent              ✅检出
  载荷放进 POST body（明文）          ✅检出
```

**绕过率从 0.5% 直接反弹到 7.8%。**

而这 4 个隐身用例，载荷一个字符都没变形——就是最规矩的 `union select`。

## 七、第四类根因：字段白名单（架构级问题）

原因很简单，我第一版的检测面是这么写的：

```python
blob = " ".join(str(rec.get(k, "")) for k in ("url", "ua", "body", "referer"))
```

四个字段，硬编码白名单。Cookie、X-Forwarded-For、Accept-Language、任意自定义 Header——**这些字段我压根没读**。

把攻击载荷放进 `X-Forwarded-For` 是个什么场景？非常常见：很多应用会把 XFF 写进访问日志或数据库，于是它成了 SQL 注入和日志注入的经典入口。而我的引擎对这个字段的存在一无所知。

JSON body 里那条更隐蔽：载荷写成 `{"keyword":"\u0075nion select"}`，服务端 `json.loads` 之后会还原成完整关键字，但日志里躺着的是转义形式——**检测看到的是转义后的串，执行看到的是还原后的串，又一次语义不一致**。

这个错误比前三个坑都低级，但危害最大：

- 前三个坑是"某个手法防不住"，影响面是**一类变形**
- 字段白名单是"某个位置看不见"，影响面是**所有攻击类型**

修法也很直白——不要枚举"我认为重要的字段"，遍历所有字段：

```python
def collect_blob(rec):
    parts = []
    for k, v in rec.items():
        if isinstance(v, str):
            parts.append(v)
        elif isinstance(v, dict):          # headers 之类的嵌套结构
            for kk, vv in v.items():
                parts.append(str(kk)); parts.append(str(vv))
        elif isinstance(v, (list, tuple)):
            parts.extend(str(x) for x in v)
    return " ".join(parts)
```

修完：**协议层 8/8 全部检出**。

顺带在归一化层补了三件事：`\uXXXX` 转义还原、UTF-7 还原、`CHAR(117,110,...)` 折叠、NFKC 全角归一化、同形字映射。其中 `CHAR()` 那条我犹豫过要不要算"加规则"——最后还是放进了归一化层，理由是**它是编码手段而非语义等价**，`char(` 加数字列表是有明确语法特征的，不需要真的懂 SQL。

## 八、剩下那些：我故意不补

两轮全部修完，最终**绕过率 2.9%**（346 个用例，剩 10 条），回归仍是 100% / 0%。

剩下的是什么？

**9 条是 `CHAR()` 部分编码。** 这个结果挺有意思：我把关键词**完整**编码的情况解决了，`char(117,110,105,111,110)` 会被折叠回 `union` 然后命中。但只编码**一半**的情况解决不了——

```
原始：    union select
部分编码：char(117,110,105,111,110) sele      ← 前半编码，后半明文
```

这种检测不到，因为关键词不再以连续字符串的形式出现，而我的检测依赖连续串。要覆盖它，得知道"前半段编码结果 + 后半段明文 = 一个完整关键字"——这需要**执行**，不是字符串处理能做到的。

**1 条是等价操作符替换**（`||` 代替 `or`、`2>1` 代替 `1=1`），就是第一轮剩下的那条。

我为什么不补？

因为要检出它，我得**真正理解 SQL 表达式的语义**——知道 `||` 是逻辑或、知道 `2>1` 是恒真条件。这不是字符串处理能做到的，需要词法分析 + 语法树 + 常量折叠。

补到这一步，说明我的方案已经触碰到了它的能力边界：**正则 + 归一化能覆盖语法层，覆盖不了语义层。**

而我认为**把这个边界如实写出来，比把它藏起来有价值**。因为一个声称"零绕过"的检测系统，只有两种可能：要么它没测过，要么它没告诉你测了什么。

## 九、四条方法论（这是我最想留下的）

### 1. 归一化层 > 规则库

规则库和变形手法是**一对多的关系**，你永远补不完。归一化是把"多"折叠回"一"，投入产出比高一个量级。

我这轮规则数量一条没加（只修了缺陷），覆盖面从 87.7% 提到 99.5%。

### 2. 顺序是归一化层的第一性问题

`URL解码 → 还原超长编码` 和 `还原超长编码 → URL解码`，看起来只是两行代码换个位置，实际结果一个是乱码一个是正确答案。

**每一步归一化都会改变后续步骤的输入。** 设计归一化链时，必须明确每一步的前置条件。

### 3. 先分清"规则缺陷"和"绕过手法"

判断方法极其简单：**原始写法能不能检出？**

- 不能 → 规则缺陷，去改规则
- 能 → 绕过手法，去补归一化

把这两种混为一谈，会导致你在错误的方向上越走越远。

### 4. 不要用白名单定义"攻击会出现在哪"

我枚举了 `url / ua / body / referer` 四个字段，等于向攻击者宣告：其他位置随便来。

正确做法是遍历所有字段。**载荷会出现在哪里由攻击者决定，不由我决定。**

这条不只适用于日志检测——凡是"我只检查这几处"的设计，都默认了对手会守规矩。

---

## 十、局限性（照例写在最后）

- **30 种手法是我能想到的，不是全部。** 真实攻击者的想象力比我强。分块传输编码（chunked）、HTTP 请求走私（CL.TE / TE.CL）、慢速攻击（Slowloris）、多参数拼接、HTTP/2 头部压缩差异，我仍然没测。
- **变形 ≠ 真实攻击。** 我测的是"能不能绕过检测"，没测"变形后还能不能在服务端执行成功"。有些变形可能两边都失效。
- **346 个用例仍然是小样本。** 不能外推到真实流量。
- **没有语义层。** 就是剩下那 2.9%——`||` 等价替换、`CHAR()` 部分编码，都需要"执行"才能判断，字符串层做不到。

所以 2.9% 这个数字同样不代表真实效果，而且**我敢说它一定还是被高估了的**——因为我的测试集里没有请求走私，没有慢速攻击，没有那些我想不到但真实存在的手法。

它的意义在于：**我现在有一套能持续发现盲区的流程**。明天有人告诉我一种新的绕过手法，我能在 5 分钟内知道它是否会打穿我的规则、打穿在哪一步。

## 写在最后

第一轮结束时我以为自己到终点了，0.5% 看着像个能拿出去说的数字。

然后我补测了协议层，一夜回到 7.8%。

这件事给我的冲击比任何一个具体的技术点都大：**我当时之所以觉得 0.5% 可信，是因为我只在自己想到的维度里测。** 维度是我想出来的，那这个数字本质上是在测量我的想象力上限，不是在测量系统的强度。

所以现在我对"绕过率 2.9%"这句话的态度是：**它是我目前能想到的所有维度下的结果，真实值一定更高。**

回头看这两篇，第一篇我学会了"指标口径容易被动手脚"，这一篇我学会了**"没被攻击过的指标，等于没测过；而只在你自己想到的维度里做过的攻击，等于只测了一半"**。

上一篇结尾我说"价值不在数字，而在于我建立了一套能算出这个数字的流程"。这次补上后半句：**这套流程还必须包含"攻击自己"这一环，而且这一环的测试维度本身也要持续被质疑——否则你永远不知道自己的边界在哪。**
