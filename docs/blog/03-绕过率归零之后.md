# 绕过率归零之后：我发现真正的问题不在规则，在我自己

> 前情：第一篇我《把检出率从 88.9% 做到 100%》，第二篇我《写了个脚本攻击自己的检测规则》，绕过率从 12.3% 打到 2.9%，并留下了"剩下 2.9% 是语义层，正则做不到"的结论。
>
> 这一篇是第三轮。结论是：**那 2.9% 里，8 条是我测试脚本自己的 bug。而在修它的过程中，我意外发现自己上一篇文章里那个 100%，其实是碰巧成立的。**

## 二、8/10 的"盲区"是测试脚本的 bug

上一轮那 10 条漏报里，9 条被我归因于"`CHAR()` 部分编码，关键字被从中间切断，需要语法树才能识别"。听起来很专业，对吧？

实际去看才发现，`m_char_func` 是这么写的：

```python
def m_char_func(s):
    head = s[:12]                      # ← 只取前 12 个字符
    codes = ",".join(str(ord(c)) for c in head if ord(c) < 128)
    return "char(%s)" % codes          # ← 后面的载荷，直接丢了
```

它把载荷截断成前 12 个字符，剩下的**一个字都没保留**。

于是变形后的字符串被归一化还原出来是这种东西：

```
原始：1' union select null,version()--
变形：char(49,39,32,117,110,105,111,110,32,115,101,108)
还原：1' union sel          ← select 被截成 sel，后面的全没了
```

`sel` 不是 `select`，检测规则当然不认它。**但它也不可能被 MySQL 执行**——它根本不是一个完整的攻击。

我把一个"被我自己的脚本截残的字符串"当成了"检测引擎的能力边界"，还给它写了一段"需要语法树才能解决"的技术分析。

修正后的版本：编码一个**完整关键字**，载荷一字不丢。

```python
def m_char_func(s):
    low = s.lower()
    for kw in ("union", "select", "script", "alert", "sleep", ...):
        i = low.find(kw)
        if i >= 0:
            seg = s[i:i + len(kw)]
            codes = ",".join(str(ord(c)) for c in seg if ord(c) < 128)
            return s[:i] + "char(%s)" % codes + s[i + len(kw):]   # 前后都保留
```

改完之后这 8 条全部检出——不是因为我改进了检测规则，是因为**攻击载荷终于完整了**。

**教训：对抗测试的结果，取决于测试工具本身是对的。而我此前从未验证过它。**

## 三、给测试工具加自测：变形还算是"同一个攻击"吗

既然 `mutate.py` 自己会出错，那它就得有自己的测试。我加了一个有效性校验，判据是**信息保留**：

```python
def variant_effectiveness(base, variant):
    norm = (detect.deep_normalize(variant) + " " +
            detect.deep_normalize(variant, comment_to_space=True)).lower()
    # 1. 长度不能大幅缩水（截断会直接丢信息）
    if len(variant) < len(base) * 0.6:
        return False, "载荷被截断（%d → %d 字符）" % (len(base), len(variant))
    # 2. 原始载荷里的实词，归一化后至少保留一半
    words = [w for w in _WORD_RE.findall(base.lower()) if w not in _STOP]
    if words:
        kept = [w for w in words if w in norm]
        if len(kept) < len(words) * 0.5:
            return False, "实词丢失 %d/%d" % (len(words) - len(kept), len(words))
    return True, ""
```

这里有个细节值得说：判据用的是**词表**（`union`/`select`/`version` 这些实词是否还在），不是检测规则的正则。如果我用"检测引擎能否检出"来判断变形是否有效，那就成了循环论证——检不出的都算无效，绕过率永远是 0。

### 但第一版这个校验也是错的

我最初把校验放在了"未检出"分支里：

```python
if not hit:
    ok, why = variant_effectiveness(base, variant)   # ← 只在漏报时才跑
```

**这意味着：一旦绕过率归零，这个校验一次都不会执行。** 它会输出一个"无效变形：0 条"的漂亮数字，而这个数字什么都没验证过。

改成无条件执行之后，实测调用 **338 次**（346 个用例里 8 个是基线不变形），全部保真。这次的"0"才是有意义的。

**教训：一个只在失败时才运行的检查，等于没有检查。**

## 四、顺手挖出来的真 bug：我上一篇文章里那个 100% 是碰巧的

改完之后我顺手重跑了真实日志那轮实验（452 条自建靶场日志），结果：

```
检出率 88.9% ｜ 误报率 0.0% ｜ F1 94.1%
```

**从 100% 掉到 88.9%。** 8 条登录爆破请求被判成漏报。

查下来的根因让我有点难受：

```python
def make_alert(rule_id, rule_name, level, rec, evidence):
    return {"ts": now_str(), ...}        # ← 打的是"运行时刻"
```

行为规则（R7 突发、R8 爆破）触发时，告警时间戳用的是**脚本运行那一刻的墙上时间**，而日志里请求的时间来自日志本身。下游做"事件与请求关联"时用的是 120 秒窗口：

```python
if e.get("src_ip") == ip and abs(ts - ets) <= EVENT_WINDOW:
```

- 上一轮跑实验时，日志是几分钟前刚生成的 → 时间差小于 120 秒 → 关联成功 → **100%**
- 这一轮跑实验时，日志是几小时前生成的 → 时间差 27112 秒 → 关联永远失败 → **88.9%**

也就是说：**我第一篇博客里那个 100%，有一部分是靠"我恰好在生成日志后不久就跑了检测"才成立的。** 换个人、换个时间跑同一份代码，就会得到 88.9%。而我在文章里把这个数字当成了系统的能力。

修法是一行——让事件携带触发它的那条请求的时间：

```python
def make_alert(rule_id, rule_name, level, rec, evidence, ts=None):
    if ts is None:
        ts = now_str()
    elif isinstance(ts, (int, float)):
        ts = datetime.datetime.fromtimestamp(ts).strftime("%Y-%m-%d %H:%M:%S")
```

修完回到 **100% / 0%**，而且这次是真的。

**教训：事件时间 ≠ 处理时间。这是流式检测里最容易错的一处，而我错了整整两篇文章。**

## 五、那 2 条真盲区怎么解决的

排除掉 8 条脚本 bug，剩 2 条是真的：

### 1. 等价操作符替换：`admin' || 2>1--`

`||` 等价于 `or`，`2>1` 等价于 `1=1`。这是真正的语义层问题——字符串层面毫无共同点。

我在第二篇里说"需要语法树，正则做不到"，这话没错，但**我没说"所以我就不做了"**。第三轮我加了一个最小语义层：词法化 → 操作符等价归一 → 常量折叠 → 序列匹配。

核心是常量折叠这一步：

```python
def fold_constants(toks):
    """2>1、1=1、'a'='a' → __TRUE__"""
    ...
    if k == "num" and toks[i+1][0] == "op" and toks[i+2][0] == "num":
        val = cmp_op[toks[i+1][1]](float(v), float(toks[i+2][1]))
        out.append(("const", "__TRUE__" if val else "__FALSE__"))
```

折叠之后，`1=1` 和 `2>1` 变成同一个 `__TRUE__`，`||` 和 `or` 变成同一个 token。于是规则里那条 `or\s+1\s*=1` 不再是唯一能匹配的形态：

```python
# S1 永真条件：or / and / xor 之后 4 个 token 内出现恒真表达式
for i, (k, v) in enumerate(toks):
    if k == "id" and v in ("or", "and", "xor"):
        if any(t[0] == "const" and t[1] == "__TRUE__" for t in toks[i+1:i+5]):
            hit("S1", "永真条件（语义层）", ...)
```

这不是完整的 SQL 解析器——没有语法树，没有执行语义。但几十行就换来了语义层的一部分覆盖，而且**边界是清楚的**：真正的语义等价（比如 `mid(user(),1,1)='r'` 这种函数等价）它依然抓不到。

### 2. 双写关键词：`ununionion`

双写是对付"把关键字替换成空串"的过滤器的——删一次还剩一个。所以检测方不该删关键字，而该把重叠双写折回去：

```python
def _fold_double_write(s):
    """kw[:h] + kw + kw[h:] → kw"""
    for kw in ("union", "select", "script", ...):
        for h in range(1, len(kw)):
            pat = kw[:h] + kw + kw[h:]
            if pat in s.lower():
                s = re.sub(re.escape(pat), kw, s, flags=re.I)
```

## 六、0% 之后我该做什么：承认采集层的边界

346 个用例全过之后，我没有继续加手法，而是加了一组**性质完全不同**的用例——不是"载荷怎么变形"，而是"日志里有没有这个东西"：

| 用例 | 场景 | 结果 |
|---|---|---|
| C1 | URL 被采集层截断，载荷落在截断线之后 | ❌ 不可见 |
| C2 | POST body 未采集（配置只记 URL） | ❌ 不可见 |
| C3 | 分块传输：body 分片，日志只落首片 | ❌ 不可见 |
| C4 | 请求走私：外层合法，内层载荷不可见 | ❌ 不可见 |
| C5 | HTTPS 加密链路：中间设备只看到 SNI | ❌ 不可见 |

5 个全瞎。而且**这 5 个不是改检测规则能解决的**——输入里根本没有载荷。

我把它们单独分组、不计入绕过率，就是为了防止自己做上一轮做过的蠢事：把"采集层问题"当成"检测规则问题"去修。**后者改代码能解决，前者只能改采集配置，混在一起会让人在错误的方向上使劲。**

这也顺带回答了一个我一直在回避的问题：这套东西的真实上限不是由规则决定的，是由**日志里记了什么**决定的。

## 七、三条方法论（第三轮才总结出来的）

### 1. 测试工具必须自己被测

我花了两轮时间分析"为什么 `CHAR()` 部分编码检测不出来"，写了很长的技术分析。最后发现是变异函数里 `s[:12]` 把载荷截断了。

**如果你的测量工具可能出错，那你测量出的每一个"盲区"都要先问一句：这真是系统的边界，还是我工具的边界？**

### 2. 检查不能只在失败时运行

有效性校验第一版写在 `if not hit:` 分支里，绕过率归零时它一次都不执行——输出"无效变形 0 条"却什么都没验证。

**一个只在出问题时才跑的检查，永远不会在你需要它的时候跑。**

### 3. 指标要经得起"换个时间再跑一次"

时间戳那个 bug 最可怕的地方是：它不会报错，不会崩溃，只是让数字从 100% 变成 88.9%。而我上一篇文章已经把 100% 当成结论发出去了。

**判断一个指标是否可信，最简单的办法是换台机器、换个时间、换个人再跑一次。能对上，它才是系统的性质；对不上，它只是那次运行的巧合。**

## 八、局限性（照例，而且这次它更重要）

- **0% 依然只是"我能想到的 30 种手法"下的 0%。** 上一轮 0.5% 的时候我也以为到终点了。**维度的上限是我的想象力，不是系统的强度。**
- **有效性校验的判据是词表保留率**，它能抓住"截断"，抓不住"语法正确但语义变了"的变形。
- **语义层不是解析器。** 没有语法树，没有常量传播，函数等价（`substr` vs `mid`）、变量替换、编码函数嵌套都抓不到。
- **采集层 5 类盲区完全无解**，只能靠改采集配置（记录 body、不做 URL 截断、解密流量）。
- **数据仍然全部自建。** 452 条来自我的靶场，346 个用例来自我的载荷库。真实流量一次都没验证过。

## 写在最后

这三轮下来，我改的规则其实不多——归一化层加了双写折叠，新增了 5 条语义层规则。**真正的变化是我对"数字"的态度。**

- 第一篇：拿到 100%，我觉得搞定了。（后来发现部分靠运气）
- 第二篇：拿到 0.5%，我觉得到边界了。（后来发现维度是自己想出来的）
- 第三篇：拿到 0%，我先去查我的脚本。（查出 8 条假盲区 + 1 个真 bug）

现在如果有人问我"你这个 100% 可信吗"，我的回答是：**在我自己造的数据、自己想的手法、自己写的规则下，它是真的。它的意义不在于这个数字本身，而在于我现在有一套流程，能说清楚这个数字是怎么来的、它在什么条件下会变、以及它没覆盖什么。**

比起一个漂亮的检测结果，我认为这套"不断质疑自己上一版结论"的流程，才是这个项目真正做出来的东西。
