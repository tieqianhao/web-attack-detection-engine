# 我是怎么把检出率从 88.9% 做到 100% 的

> 副标题：搭一个 Web 攻击检测平台不难，难的是你凭什么说自己那个数字是真的

---

## 写在前面

网上"我搭了个 ELK"的教程很多，点开基本都是同一个套路：起三个容器、配一下 Filebeat、贴两张 Kibana 截图，然后就结束了。

这类文章我读完总有个疑问：**你的检测规则到底有没有用？**

没人回答这个问题。因为回答它需要一样绝大部分人没做的东西——**真值（ground truth）**。没有真值，你就只能说"我配了 6 条规则"，而不能说"我的规则在 452 条日志上做到了 100% 检出、0% 误报"。

这篇记录我搭这个平台的完整过程，重点是**三轮指标复盘**：从 88.9% 到 100%，中间还一度出现过"100% 检出但 100% 误报"的荒唐结果。

我觉得这个过程比最终结果有价值得多——因为它暴露了一个事实：**指标口径稍微松一点，你就能给自己一个漂亮到假的数字。**

---

## 一、先说清楚这个平台长什么样

### 为什么要做

我之前的经历基本都在攻击侧：靶场、漏洞复现、论文。有个很明显的问题——**我不会防守**。

面试官问"你怎么发现有人在打你"，我答不上来。所以我决定补上这块，目标很明确：做一个人能做完、能跑出数字、能写进简历的检测项目。

### 架构

```
流量 → 靶场应用 → Nginx 格式访问日志
                        ↓
              解析 + 规范化（normalize）
                        ↓
        特征规则（6 条）+ 行为规则（2 条）
                        ↓
              告警 → 报告 → 看板
                        ↓
                真值比对 → 算指标
```

关于"真 ELK"：我配了 docker-compose（ES + Kibana + Filebeat），但当时 Docker Desktop 没开。所以我先做了**免 Docker 版**——检测逻辑完全一致，只是日志存本地文件而不是 ES。

回头看这个决定是对的：**先把检测逻辑和指标闭环跑通，再升级存储层，顺序不能反。** 一上来就堆组件，最后只会得到一个能看图的空壳。

### 三个关键组件

**1. 靶场（vuln_app.py）**

一个故意留了漏洞的 Flask 应用：SQL 注入、路径遍历、反射 XSS、登录接口。只监听 `127.0.0.1`。

**2. 流量发生器（traffic_gen.py）**

按比例生成正常流量和攻击流量，并且——这是关键——**每一条都打上标签写入 `ground_truth.jsonl`**：

```python
rec = {
    "ts": time.time(),
    "path": path,
    "ua": ua,
    "label": "attack" if label != "normal" else "normal",
    "attack_type": label,   # sqli / xss / traversal / sensitive / sqli_encoded ...
    "status": status,
}
```

**3. 检测与评估（detect.py + run_pipeline.py）**

6 条特征规则 + 2 条行为规则，跑完和真值比对，直接输出混淆矩阵和四个指标。

## 二、第一轮：88.9%，漏的全是"编码过的"

第一次跑完：

```
日志 452 条 ｜ 告警 86 条
检出率 88.9% ｜ 误报率 0.0%
```

88.9% 看着还行，但我不能就这么收工。把漏报全打出来看，规律非常明显——**漏的全是 URL 编码过的攻击**。

原因一想就通：

```
原始:    /search?q=admin' union select 1,2,3--          → 正则能匹配
编码后:  /search?q=admin%27%20union%20select%201%2C2%2C3-- → 正则匹配不到
```

我的规则是拿正则直接怼原始字符串。但**后端拿到请求是会先解码再执行的**。也就是说：

> 检测层看的是编码后的字符串，执行层用的是解码后的字符串 —— 两者看到的根本不是同一个东西。

这个味道是不是很熟悉？对，就是 **parser differential（解析器差异）**。我在分析 fast-uri 双 CVE、PyJWT CVE-2026-102268 时总结过这一类根因，结果在自己的检测代码里又踩了一次。

**修复很简单**，加一个规范化：

```python
def normalize(text):
    """先解码，再匹配（多次解码防多重编码）"""
    s = text
    for _ in range(3):
        new = urllib.parse.unquote_plus(s)
        if new == s:
            break
        s = new
    return s

def signature_detect(rec):
    blob = " ".join(str(rec.get(k, "")) for k in ("url", "ua", "body", "referer"))
    blob = blob + " " + normalize(blob)   # 原始串 + 规范化串都匹配
    ...
```

加上之后，编码类攻击全部命中。

**教训一：先规范化，再检测。** 顺序反了，你的检测就是个筛子。

## 三、第二轮：指标算错了，不是规则不行

改完再跑：**还是 88.9%**。

这次我没急着改规则，而是去查那 8 条漏报到底是什么——是登录爆破。

问题来了：**爆破明明被行为规则 R8 抓到了，告警里有它，为什么算进了漏报？**

翻代码发现是我自己的锅：

```python
# 错误写法：算指标时只用了特征规则
hits = detect.signature_detect(rec)
detected = len(hits) > 0
```

而行为规则是**有状态的**：R8 要在一个窗口内累计 5 次登录失败才触发。前面的请求在触发时点上根本还没有告警，自然被判成漏报。

**修复：改成两遍扫描。** 第一遍跑完行为引擎收集所有事件，第二遍再判定每条请求的归属：

```python
# 第一遍：先跑完行为引擎，收集事件
beh = detect.BehaviorEngine()
beh_events = []
for rec in recs:
    ev = beh.feed(rec)
    if ev:
        beh_events.extend(ev)

# 第二遍：判定每条请求是否属于某个已触发的事件
def covered_by_event(rec):
    for e in beh_events:
        if e.get("src_ip") == rec.get("ip") and abs(ts - ets) <= EVENT_WINDOW:
            return True
    return False
```

**教训二：行为规则是"事件级"的，特征是"请求级"的。** 用请求级的口径去衡量事件级的检测，必然得出错误结论。

## 四、第三轮：100% 检出，但误报也 100%

改完再跑，出来一个让我愣住的结果：

```
检出率 100.0% ｜ 误报率 100.0% ｜ F1 27.5%
```

F1 只有 27.5 —— 说明这个"100% 检出"毫无意义。

原因是我把突发流量（80 条高频请求）的每一条都判成了误报。但我注入这段流量的本意是**模拟一次扫描行为**，它不是 80 次独立攻击，是**一个事件**。

这里我纠结了一会儿，因为两条路都能让数字变好看，但都是错的：

- 把突发标成攻击 → 请求级检出率虚高（80 条里其实只有 1 条触发告警）
- 把突发算成正常但从分母里删掉 → 直接就是数据造假

**最后定的口径**（并且写进了报告里）：

1. 正常流量只用特征规则判定 → 突发流量不会被整段算成误报
2. 攻击流量若被行为事件覆盖，也算检出 → 爆破的功劳不丢
3. 突发扫描由 R7 在**事件级**单独统计，不进请求级指标

```python
is_attack = bool(t and t.get("label") == "attack")
detected = sig_hit or (is_attack and covered_by_event(rec))
```

再跑：

```
检出率 100.0% ｜ 误报率 0.0% ｜ F1 100.0%
命中 72 ｜ 漏报 0 ｜ 误报 0 ｜ 正确排除 380
```

**教训三：口径必须在算之前定清楚，而且要写出来。** 事后调口径和一个字不改地改数据，本质上没区别。

## 六、我必须说的局限性（不然这数字就是骗人的）

**100% 这个数字，在我自己的实验里是真的，但它绝对不代表真实效果。** 必须把话说清楚：

1. **流量是我自己造的。** 攻击样本来自我自己的脚本，真实攻击者的变形手法远不止 URL 编码这一种。
2. **特征规则本质上很容易绕。** 分块传输、HTTP 参数污染、非常规编码、慢速攻击，这套规则基本都拦不住。
3. **样本量太小。** 452 条日志、72 条攻击，放到真实环境里就是几秒钟的量。
4. **没有做时间窗口外的验证。** 我没法保证换一批流量还是这个数字。

所以如果有人问"你的规则真的 100% 吗"，诚实的回答是：

> 在我构造的这组数据上是 100%，它有明确的边界。我做这件事的价值不在于这个数字，而在于**我建立了一套能算出这个数字、并且能定位每一条漏报的流程**。

有了这套流程，换一批流量、加新的绕过手法，我能立刻知道掉到多少、掉在哪里、该补什么——**这才是项目真正的能力，而不是那个数字。**

## 七、三个可以迁移到别处的方法论

**1. 没有真值，就没有指标。**
做任何检测类项目，第一件事是想办法拿到标签，哪怕是手工标的。否则你所有的"效果很好"都是自我感觉。

**2. 先规范化，再检测。**
检测层和执行层必须看到同一个东西。这条不只适用于日志检测——文件上传的后缀判断、Content-Type 校验、WAF 规则，全是同一个坑。

**3. 请求级和事件级要分开算。**
行为类检测（频率、序列、爆破）天生是事件级的。把它们塞进请求级的混淆矩阵，得到的一定是错的结论。

---

## 八、接下来我会做什么

- 加**多重编码**和**分块传输**的样本，看规则掉到多少
- 加**慢速攻击**检测（低频但持续的扫描，现在的 R7 抓不到）
- 把规则改成**加权打分**而不是命中即告警，降低将来的误报
- Docker 起来之后接真 ELK，把检测逻辑迁到 ES 查询上

## 最后

我做这个项目的初衷是补蓝队短板。做完之后发现最大的收获不是学会了 ELK，而是**学会了对自己的数字保持怀疑**。

第一次跑出 88.9% 的时候，如果我直接写"检出率约 89%"，没人会质疑。第三次跑出"100% 检出 / 100% 误报"的时候，如果我选择性地只报检出率，也没人会质疑。

但那样做出来的东西，我自己心里知道是虚的。

**能定位到每一条漏报、能说清楚每一个数字的来历——我觉得这比数字本身重要得多。**
